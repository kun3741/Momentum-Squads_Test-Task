# План майбутнього розгортання

Зараз Docker лишається конфігурацією в репозиторії. Власник попросив не встановлювати Docker на VPS; наведені нижче команди описують можливий майбутній запуск **лише на хості, де Docker уже доступний**, або після окремого рішення власника щодо способу розгортання. Жодна з них не виконана на VPS.

Перед майбутнім запуском перевірте вільні ресурси командами `df -h /` і `free -h`. Орієнтир для цього стеку разом із запасом під образи, БД і оновлення: щонайменше 2 ГБ RAM і кілька ГБ вільного диска після встановлення Docker; практично зручніше мати 20 ГБ загального диска. Фактичне споживання потрібно виміряти після запуску.

## Підготовка сервера

1. Переконайтеся, що нинішні сервіси на 80/443 залишаються потрібними, і перевірте резервні копії перед будь-яким очищенням диска. Не видаляйте їхні дані заради цього проєкту.
2. На хості з уже доступним Docker Engine і Compose plugin клонуйте репозиторій у окремий каталог і перейдіть у нього. Не змінюйте файли інших проєктів.
3. Скопіюйте `.env.example` в `.env`, встановіть `chmod 600 .env`, задайте випадкові значення для `POSTGRES_PASSWORD`, `OPERATOR_PASSWORD`, `WEBHOOK_SECRET`. Для пароля PostgreSQL використайте URL-безпечні символи, наприклад `openssl rand -hex 24`: Compose формує з нього `DATABASE_URL`.

## Безкоштовний стабільний тунель

Для постійних посилань у відповідях зручний безкоштовний dev-домен ngrok: [ngrok документує](https://ngrok.com/docs/gateway/domains), що такий домен закріплюється за обліковим записом і не змінюється після перезапуску агента. Безкоштовний план має [ліміти](https://ngrok.com/docs/pricing-limits), зокрема 20 000 HTTP-запитів на місяць і 1 ГБ вихідного трафіку; для демонстрації цього завдання їх може вистачити, але для постійного навантаження потрібно оцінити фактичне використання. На безкоштовному плані браузер може показувати проміжне попередження перед HTML-сторінками.

1. Створіть безкоштовний акаунт ngrok та знайдіть свій призначений dev-домен і authtoken. Не комітьте token і не надсилайте його в чат.
2. У `.env` встановіть `NGROK_AUTHTOKEN` та `PUBLIC_BASE_URL=https://<ваш-dev-домен>`. Саме ця адреса з'явиться в посиланнях на статті, які отримають клієнти.
3. Запустіть `docker compose --profile tunnel up --build -d`. Профіль запускає контейнер `ngrok/ngrok`, який спрямовує публічний HTTPS на `api:8000`. API й мок слухають хост лише на loopback; nginx та його порти 80/443 не змінюються.
4. Перевірте `docker compose ps`, `docker compose logs --tail=100 ngrok api worker` та `curl -i http://127.0.0.1:8000/ready`. Потім перевірте `https://<ваш-dev-домен>/health` із зовнішньої мережі.
5. Запустіть `python3 tests/integration.py` на VPS. Тест звертається до локальних портів 8000/8001, створює синтетичні звернення та перевіряє дублікати, модерацію й повтори. Після нього перевірте доступ оператора через HTTPS і посилання на статті в чернетці.

Для короткої демонстрації без реєстрації існує [Cloudflare Quick Tunnel](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/), але його випадковий домен змінюється після перезапуску. Тоді `PUBLIC_BASE_URL` і посилання в уже створених чернетках застаріють. Для цього сервісу стабільний домен кращий.

## Подальша експлуатація

- Вебхук: `https://<ваш-dev-домен>/webhooks/helpdesk` із заголовком `X-Webhook-Secret`.
- Інтерфейс оператора: `https://<ваш-dev-домен>/` з HTTP Basic користувачем `operator` і паролем `OPERATOR_PASSWORD`.
- PostgreSQL зберігається в Docker volume `pgdata`; налаштуйте його резервне копіювання. `docker compose down -v` видаляє дані.
- Не підключайте справжній хелпдеск без перевірки, що він підтримує ідемпотентні POST-відповіді за сталим ключем. Наявний мок таку гарантію забезпечує.
- Якщо зміниться тунельний домен, оновіть `PUBLIC_BASE_URL` і перезапустіть воркер перед новими зверненнями. Уже створені чернетки можуть містити старий домен.
