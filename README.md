# Orbita support drafts

Невеликий сервіс підтримки для вигаданого продукту Orbita. Вебхук приймає звернення, воркер знаходить статті бази знань і готує чернетку за допомогою LLM. Оператор переглядає або редагує чернетку та підтверджує чи відхиляє її. Підтверджену відповідь воркер надсилає в мок хелпдеску.

## Вимоги

- Docker Engine з Compose v2.
- Python 3.12 для запуску інтеграційного тесту з хоста (для самого сервісу Python на хості не потрібен).
- Інтернет для першого збирання образів і для запиту до LLM-провайдера.

## Запуск

1. Скопіюйте `.env.example` в `.env`. Для локальної перевірки можна лишити значення за замовчуванням. Перед публічним доступом задайте випадкові `POSTGRES_PASSWORD`, `OPERATOR_PASSWORD` і `WEBHOOK_SECRET` та HTTPS-адресу `PUBLIC_BASE_URL`.
2. Виконайте `docker compose up --build -d` у корені репозиторію. Без `.env` Compose не запуститься: три основні секрети обов'язкові.
3. Перевірте `http://localhost:8000/health`: відповідь має бути `200 OK` з тілом `OK`.
4. Відкрийте `http://localhost:8000/`. HTTP Basic авторизація: користувач `operator`, пароль з `OPERATOR_PASSWORD` (локально `change-me`).
5. Логи: `docker compose logs -f api worker mock-helpdesk`. Зупинка: `docker compose down`. Дані PostgreSQL лишаються в томі `pgdata`; `docker compose down -v` видалить їх.

`api`, `worker`, `mock-helpdesk` та PostgreSQL запускаються окремими контейнерами. Одноразовий контейнер `init` створює таблиці й додає 8 статей бази знань. Схема наразі створюється через `create_all`; міграції ще не додані.

### Приклад звернення

У PowerShell:

```powershell
$body = @{
  event_id = 'evt_demo_1'
  ticket_id = 'T-DEMO-1'
  customer_email = 'user@example.com'
  message = 'Не можу експортувати звіт у PDF'
  reply_url = 'http://mock-helpdesk:8001/tickets/T-DEMO-1/replies'
} | ConvertTo-Json
Invoke-RestMethod -Uri http://localhost:8000/webhooks/helpdesk -Method Post -ContentType 'application/json' -Headers @{ 'X-Webhook-Secret' = 'local-webhook-secret' } -Body $body
```

Секрет у прикладі відповідає `.env.example`; якщо ви його змінили, підставте нове значення. `reply_url` використовує внутрішнє DNS-ім'я Docker Compose: браузер або PowerShell з хоста не повинні відкривати цю адресу. Вебхук повертає `202` після запису події в PostgreSQL, не чекаючи LLM. Без API-ключа виклик провайдера й очікування разом займають 5–30 секунд; після цього чернетка з'явиться в інтерфейсі. Перед підтвердженням її можна відредагувати. Список звернень має сторінки по 100 записів.

Після підтвердження мок прийме відповідь. Для перегляду записаних відповідей:

```powershell
Invoke-RestMethod -Uri http://localhost:8001/replies -Headers @{ 'X-Mock-Admin-Secret' = 'local-webhook-secret' }
```

Порти API й мока відкриті лише на `127.0.0.1` хоста. Відповідь не надсилається реальній людині.

## API

| Метод і шлях | Призначення | Авторизація |
|---|---|---|
| `GET /health` | `200` і текст `OK` | Немає |
| `POST /webhooks/helpdesk` | Зберегти подію, `202` | `X-Webhook-Secret` |
| `GET /` | Список звернень і форми модерації | HTTP Basic |
| `GET /api/tickets/{ticket_id}` | Стан і чернетка одного звернення | HTTP Basic |
| `POST /tickets/{id}/approve` | Підтвердити відредаговану чернетку | HTTP Basic і `review_token` з форми |
| `POST /tickets/{id}/reject` | Відхилити чернетку | HTTP Basic і `review_token` з форми |
| `GET /kb/{slug}` | Стаття бази знань | Немає |

Тіло вебхука містить обов'язкові `event_id`, `ticket_id`, `customer_email`, `message`, `reply_url` згідно з умовою завдання. URL відповіді має точно відповідати дозволеному origin та шляху `/tickets/{ticket_id}/replies`. Повтор того самого `event_id` для того самого `ticket_id` повертає `202`; повтор з іншим `ticket_id` повертає `409`. Неавторизований запит повертає `401`, некоректні дані — `422`. Якщо PostgreSQL тимчасово недоступний або заблокований, вебхук повертає `503` для повторної доставки. Для API задано короткі таймаути підключення й пулу, а для транзакції вебхука — таймаути очікування блокування та SQL-запиту. Один `ticket_id` створює одну чернетку, навіть якщо події мають різні ID.

OpenAPI-схема FastAPI доступна за `/openapi.json`, інтерактивний опис — за `/docs`.

## LLM і база знань

Вісім коротких статей описують PDF і CSV експорт, пароль, командні запрошення, оплату, синхронізацію, фільтри та API-токен Orbita. Пошук рахує збіги слів із заголовками й ключовими словами та передає до трьох статей у запит до моделі. Посилання в чернетці будуються від `PUBLIC_BASE_URL`.

За наявності `OPENAI_API_KEY` сервіс викликає OpenAI Chat Completions (`OPENAI_MODEL`, за замовчуванням `gpt-4o-mini`). Якщо модель не включила посилання на знайдені статті, сервіс додає їх до чернетки. Без ключа він **все одно виконує HTTP-запит до провайдера**, потім замінює його відповідь статичною чернеткою. Загальна затримка цієї гілки випадкова в межах `MOCK_LLM_DELAY_MIN`–`MOCK_LLM_DELAY_MAX` (за замовчуванням 5–30 секунд). Помилки з наявним ключем призводять до повторної спроби; вони не маскуються статичною відповіддю.

PostgreSQL лічить початки LLM-викликів за рухомі 60 секунд. Транзакційний advisory lock серіалізує резервування ліміту між воркерами. За замовчуванням воркер має 32 потоки; це налаштовується через `WORKER_CONCURRENCY`.

## Надійність і межі гарантій

- Подія записується до відповіді вебхука. Унікальні ключі PostgreSQL обробляють одночасні дублікати. Якщо запис у БД не вдався, вебхук не повертає `202`, тож відправник може повторити доставку.
- Воркер забирає записи через `FOR UPDATE SKIP LOCKED`. Після падіння процесу незавершену задачу повертає в роботу час оренди (120 секунд). Помилки LLM і хелпдеску повторюються з обмеженою експоненційною затримкою.
- Мок хелпдеску зберігає `Idempotency-Key: reply:{ticket_id}` і не створює другий запис після таймауту, навіть якщо перший запит уже записав відповідь. Для справжнього хелпдеску **потрібна така сама гарантія на його боці**. Без підтримки ідемпотентності зовнішнім API неможливо одночасно автоматично повторювати неоднозначні таймаути і гарантувати, що клієнт ніколи не отримає дубль.
- Мок підтримує сценарії `500` та `timeout-after-write` через `PUT /scenarios/{ticket_id}` з заголовком `X-Mock-Admin-Secret`. Значення `normal` повертає звичайну поведінку.

## Перевірка

Після запуску Compose виконайте `python tests/integration.py`. Скрипт перевіряє 12 паралельних повторів одного вебхука, час відповіді до 2 секунд, появу чернетки, модерацію, одну відправлену відповідь, повтор після таймауту з уже записаною відповіддю, відновлення після `5xx` і відхилення чернетки. Тест використовує випадкові ID й читає секрети з `.env` або змінних середовища. Типовий час виконання — до кількох хвилин через навмисну затримку LLM.

Для запуску проти локальних сервісів на інших портах налаштуйте `BASE_URL`, `MOCK_BASE_URL` та `HELPDESK_ALLOWED_ORIGIN`. Остання змінна задає origin, який вставляється в `reply_url` тестових вебхуків. Результат фактичної перевірки наведено в [TESTING.md](TESTING.md).

Для локальних модульних тестів встановіть залежності з `requirements.txt` і виконайте `python -m pytest -q tests/test_contract.py`. Для швидкої перевірки синтаксису: `python -m compileall -q app tests`.

GitHub Actions запускає ці перевірки та інтеграційний сценарій у Docker Compose для кожного push у `main` і кожного pull request. Логи контейнерів зберігаються в журналі невдалого запуску.

## Підготовка до VPS

Для публічного тунельного домену задайте `PUBLIC_BASE_URL` як HTTPS-адресу тунелю, замініть усі прикладові паролі й секрети, обмежте доступ до операторського інтерфейсу та забезпечте резервне копіювання тому PostgreSQL. `HELPDESK_ALLOWED_ORIGIN` за замовчуванням вказує на внутрішній мок. Опціональний профіль `tunnel` запускає ngrok із безкоштовним стабільним dev-доменом облікового запису. План можливого майбутнього запуску описано в [DEPLOY_VPS.md](DEPLOY_VPS.md). Docker на VPS за поточним рішенням власника не встановлюється, деплой не виконувався.
