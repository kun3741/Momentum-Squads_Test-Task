# Перевірки

## Локальна інтеграція — 6 листопада 2026 року

Тест запущено на Windows із Python 3.12 та ізольованим PostgreSQL 16.15, завантаженим як ZIP і перевіреним за SHA-256. PostgreSQL слухав лише `127.0.0.1:55432`; API, воркер і мок хелпдеску були окремими локальними процесами. Зовнішній API-ключ LLM не використовувався: воркер виконав реальні HTTP-запити до провайдера, отримав `401` і застосував статичну відповідь із тестовою затримкою 5 секунд.

`python tests/integration.py` пройшов чотири сценарії:

1. 12 одночасних копій одного вебхука повернули `202` менш ніж за 2 секунди, з'явилася одна чернетка, після схвалення мок зберіг одну відповідь.
2. Мок записав відповідь до таймауту HTTP-клієнта; повторне відправлення зі сталим `Idempotency-Key` лишило один запис і перевело звернення в `sent`.
3. Після тимчасового `5xx` воркер повторив відправлення й завершив його після відновлення мока.
4. Відхилена чернетка перейшла в `rejected` і не потрапила до мока.

Перший запуск тесту виявив помилку тестового клієнта: він надсилав форму схвалення як JSON. Запит виправлено на `application/x-www-form-urlencoded`, після чого всі чотири сценарії пройшли. Тимчасові процеси зупинено; тестові порти більше не слухають.

## Локальна перевірка ліміту й навантаження — 6 листопада 2026 року

На окремій тестовій БД `support_capacity` без воркера виконано ще два сценарії:

- `tests/rate_limit.py` запустив 100 конкурентних резервувань LLM-слоту. Рівно 60 отримали дозвіл і рівно 60 записів з'явилися в таблиці `llm_calls`; решта 40 були відхилені лімітером.
- `tests/load_webhooks.py` надіслав 500 унікальних синтетичних вебхуків через 10 паралельних клієнтів. Усі 500 повернули `202` без повторів, кожне звернення підтверджено через операторський API. Найповільніша відповідь вебхука тривала 0,500 секунди.

Ці скрипти навмисно не запускаються без `RATE_TEST_ALLOWED=1` та `LOAD_TEST_ALLOWED=1`. Використовуйте їх лише з окремою тестовою БД: другий сценарій створює 500 звернень. API та PostgreSQL після перевірки зупинено.

## Постійні помилки й ручний повтор — 6 листопада 2026 року

На окремій локальній БД `support_failure` запущено API, воркер і мок як окремі процеси. Оновлений `tests/integration.py` пройшов усі попередні сценарії та новий: мок повернув `400`, звернення перейшло в `send_failed` без відповіді клієнту; після перемикання мока в `normal` форма ручного повтору перевела його в `sent`, мок зберіг одну відповідь. Локальні процеси після тесту зупинено.

`python -m pytest -q tests/test_contract.py` пройшов 11 тестів, включно з помилкою авторизації LLM `401` та класифікацією `302`, `400`, `408`, `429`, `503`. Тест `302` додано після інтеграційного запуску; ця мала зміна не потребує повторного запуску всього сценарію.

## Готовність API — 6 листопада 2026 року

Новий `/ready` перевірено з локальним PostgreSQL: `200 OK` при доступній БД та `503` після її зупинки. `/health` в обох випадках повернув `200 OK`, як вимагає контракт завдання. 12 unit-тестів і перевірка синтаксису пройшли. Docker Compose у цьому Windows-середовищі не запущено, тому його healthcheck і оновлений CI-крок тут не виконувалися. Локальні процеси після перевірки зупинено.

## VPS і публічний HTTPS — 6 листопада 2026 року

На VPS встановлено PostgreSQL 16 (11 нових пакетів, 0 оновлень і видалень), створено окремі роль і БД `orbita`, встановлено залежності у `/srv/orbita-support/.venv`, запущено окремі `orbita-*` systemd-сервіси та Cloudflare Quick Tunnel. Docker на VPS не встановлювався; nginx і PM2 залишилися активними. `systemd-analyze verify` пройшов для unit-файлів. PostgreSQL, API й мок слухають лише loopback.

`tests/integration.py` двічі пройшов усі п'ять сценаріїв: спершу через локальний API, потім через публічний HTTPS-домен. Публічні `/health` і `/ready` повернули `200`, інтерфейс без HTTP Basic — `401`; нова чернетка містила посилання на статтю з актуальним HTTPS-доменом. Перша спроба публічного тесту потрапила на URL, який змінився після перезапуску тунелю разом з API, і отримала Cloudflare `530`. Залежність unit-файла виправлено з `Requires` на `Wants`; після повторного перезапуску API PID тунелю зберігся, а тест на новому URL пройшов.

Quick Tunnel не гарантує постійної адреси після власного перезапуску. Дані в БД наразі тільки синтетичні; резервне копіювання для реальних даних ще не налаштоване.

## Сталий hostname sslip.io — 7 листопада 2026 року

`orbita.104-207-90-199.sslip.io` розв'язується в IP VPS `104.207.90.199`. Для нього додано **окремий** nginx vhost, не редагуючи `existing-site`; обидві версії конфігу пройшли `nginx -t` перед reload. Зовнішній HTTP-01 пробний файл повернув `200`, Certbot випустив окремий сертифікат Orbita, а `certbot renew --cert-name orbita.104-207-90-199.sslip.io --dry-run --non-interactive` успішно імітував поновлення. Установлено hook, що перечитує nginx лише після поновлення цього сертифіката.

Зовнішні `https://orbita.104-207-90-199.sslip.io/health` і `/ready` повернули `200`; операторський інтерфейс без пароля — `401`. `tests/integration.py` пройшов усі сценарії через цей HTTPS hostname. Остання синтетична чернетка мала посилання на статтю з новим доменом. До та після nginx reload чинний `https://existing-site.example/` відповів `200` з однаковими 36 678 байтами. Старий Quick Tunnel вимкнено.

## Що лишається перевірити

- Docker Compose не запущений у цьому середовищі; на VPS Docker за рішенням власника не встановлюється.
- GitHub Actions не виконав жодного кроку через блокування акаунта GitHub, пов'язане з оплатою. Це не результат тестів застосунку.
- Реальний API хелпдеску відсутній. Гарантія від дублювання доведена для мока, який підтримує ідемпотентний ключ; у реального API цю підтримку потрібно перевірити окремо.
- Навантажувальний тест відправив 500 звернень коротким інтенсивним потоком без одночасної LLM-генерації; він доводить збереження та швидке підтвердження в цьому локальному сценарії, але не повний 10-хвилинний профіль із працюючим воркером.
